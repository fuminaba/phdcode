### [2026-09-18] Evaluating Bonsai 2 27B: runtime support gates model choice, not capability
- Researched PrismML's Bonsai 2 27B (ternary-quantized Qwen3.8 27B, 5.9-7.2GB, Apache 2.0) for use in ALiRA2. Found that stock Ollama cannot load it at all: its GGUF parser has no size for the new ternary tensor types (PQ2_0 = 142, PTQ1_0 = 143) and fails with "unsupported tensor size overflows". Requires PrismML's `prism` branch llama.cpp fork, run as `llama-server` behind an OpenAI-compatible endpoint.
- Why this approach: ALiRA2 already abstracts the model backend behind `LLM_ROUTING` (model name -> OpenAI-compatible host_endpoint), so pointing a new entry at a llama-server on another port is a config change, not a code change. That abstraction holds. What does NOT hold is `tgi.unload_all_models()`, which is Ollama-native (`/api/ps` + `/api/generate` with keep_alive=0) and would silently no-op against llama-server -- reopening the marker-pdf OOM that function exists to prevent, since a resident 7-10GB model leaves no room for marker's own weights on a ~12GB-usable card. Identified fix: llama.cpp router mode's `/models/unload`, or llama-swap's TTL-based unload, rather than assuming the existing call still protects anything.
- What to remember: an abstraction that cleanly swaps a backend usually still leaks at its *escape hatches* -- the backend-specific operations added to work around a constraint (here, forcing VRAM eviction). When swapping a backend, audit those escape hatches first, because they fail silently rather than loudly: `unload_all_models()` finds nothing to unload and returns successfully. Also, generally: a model's quantization format is a separate compatibility axis from its architecture -- "architecture supported, quantization not" is a real and blocking failure mode. **Reusable concept -- worth a spaced-repetition card.**

### [2026-09-19] Bonsai 2 27B integration: a 352s reply delay from two unqueued GPU paths
- Integrated Ternary Bonsai 2 27B via a second backend (PrismML llama.cpp fork's `llama-server` in router mode on :8080, alongside Ollama on :11434), then chased a bug where a Telegram reply took 6 minutes while the live viewer showed the answer instantly. Fixed two things: `persist_turn` now runs detached instead of blocking the reply, and `embeddings.embed()` / `GenerativeService.generate_text()` now route through the same concurrency=1 Celery queue as `call_model`.
- Why this approach: the live viewer reads `turn_actions` (written per-action, live), while Telegram only sees `handle_incoming_message`'s return value — and that function awaited `persist_turn`, which embeds prompt AND output before its DB write. Measured delta between `turn_end` and the `conversation_turns` row: 352.5s. Root cause was not slowness but *contention*: ARCHITECTURE.md claimed every GPU-touching call was serialized through Celery, but only `call_model` ever was; `embed()` and `generate_text()` talked to Ollama directly. That was invisible while Ollama was the sole backend (it serialized internally via `-np 1` and released VRAM via `keep_alive`), and became a 6-minute stall the moment llama-server started holding 13.5GB of a 16.3GB card indefinitely — a 0.3GB embedding model ended up queued behind a 9B background summarization fighting for ~2.8GB of scraps. Rejected cutting Bonsai's context to free VRAM: the 96K window is the reason for using the model at all. The queue fix addresses contention at the right layer instead.
- What to remember: **a latency bug is not always a slowness bug — measure where the time is spent before optimizing what looks slow.** The model answered in 4 seconds; the delay was entirely downstream, in a step nobody thought of as being on the critical path. Second, **an architectural invariant that is documented but not enforced will hold right up until the assumption underpinning it changes.** "Everything is serialized" was effectively true only because one backend happened to serialize internally; adding a second backend broke it instantly, and nothing in the code prevented that. Third, and the concrete trap: **when funnelling work into a fixed-size worker pool, code already running inside that pool must call the work inline rather than dispatching it** — `ingest_and_index_document` runs as a Celery task and embeds every chunk, so dispatching to a `concurrency=1` queue from there would wait forever on the slot it already holds. Hence `tasks/dispatch.py`'s `in_celery_worker()` guard. **Reusable concept — worth a spaced-repetition card (all three).**

### [2026-09-21] Evaluating a deepagents/LangGraph backend swap: the framework's value-add is the part you already overrode
- Assessed migrating `tgi.GenerativeService.generate_with_tools` to LangChain's `deepagents`. Estimated ~3-5 days for parity. Found the swap boundary is clean (3 call sites in `pipeline.py`; `tooling/registry.py`'s `@tool` is near-isomorphic to LangChain's, so ~25 tools convert via one import swap), but rejected a wholesale swap in favour of either a subagent tool built in the existing loop, or a strangler-fig `agent_graph.py` behind an env flag, A/B'd against `docs/MODEL_BENCHMARK.md`'s Tier B battery.
- Why this approach: two blockers, one structural and one empirical. Structurally, LangGraph assumes it makes the model call in-process, but this project's whole GPU discipline is that exactly one line (`tgi.py:544`) dispatches to a `concurrency=1` Celery queue while tool dispatch stays in the main process to reach the event loop's asyncpg pool via `run_on_main_loop`. Moving the graph into the worker breaks every DB tool; keeping it out means writing a custom `BaseChatModel` that dispatches to Celery -- i.e. overriding the framework's core job while still paying for it. Empirically, the digest round (`tgi.py:725-800`) has no deepagents equivalent and is tuned against a recorded real failure (gemma4-26b-a4b reading an earlier digest phrasing as prompt injection and re-verifying a tool it had already called), so rebuilding it as middleware re-opens a bug that was expensive to find. On the benefit side, deepagents' virtual filesystem and store duplicate -- less transparently -- the Postgres/pgvector memory that ARCHITECTURE.md names as a design principle, and its checkpointing duplicates `turn_actions`. Only subagents (context isolation for the arxiv/pubmed research flow) were judged a genuine gain, and that's ~60 lines in the existing loop.
- What to remember: **when evaluating a framework migration, price the framework's core abstraction against the constraint that made you hand-roll yours in the first place** -- if you'd have to override the framework's main job (here, "the framework owns the model call") to preserve an existing invariant, you're paying full dependency cost for the leftovers. Second, **a clean migration boundary measures the cost of the swap, not its value**: 3 call sites made the estimate small and the decision looked easy, but the question that actually decided it was "which of its features do I want, and do I already have them?". Third, the practical pattern for any framework swap with a narrow interface: **keep both behind a flag and let an existing eval battery decide, rather than estimating** -- a migration you can delete by removing one file is a different risk class from one you have to unwind. **Reusable concept -- worth a spaced-repetition card (first and third).**
- **Addendum (same day), after asking whether deepagents prevents OOM:** it does not, and the question conflates two failures. deepagents' `SummarizationMiddleware` manages *context-window* overflow (tokens); the OOM this project actually fights is *GPU VRAM* contention on one 16.3GB RTX 5070 Ti, prevented entirely by the `concurrency=1` Celery queue and `unload_all_models()` -- neither of which deepagents can see, since it is a client-side orchestrator talking to an OpenAI-compatible URL. Sharper still: deepagents' subagents and LangGraph's parallel tool execution fan out concurrent model calls by design, so the headline feature is unusable here -- the Celery queue serializes them (no OOM, but latency becomes the sum rather than the max, i.e. zero speedup), and moving the graph into the worker would turn it into a hard deadlock against the slot it already holds. Revised plan given the user also wants claude-code-like capability (which *does* strengthen the case, for the filesystem backend and subagent context isolation): spike `CeleryChatModel(BaseChatModel)` first as the load-bearing piece, cap graph parallelism to 1 explicitly rather than letting the queue absorb it, and treat subagents as context isolation only. Noted that deepagents ships no shell tool and no permission/sandbox layer -- a large share of what makes Claude Code useful is that layer, not the loop -- and that qwen3:14b, not the framework, is the binding constraint on agentic coding here.
- **What to remember (addendum):** **"does X handle OOM?" is ambiguous in any GPU-served LLM stack, and the two answers are usually owned by different layers** -- token-budget overflow belongs to the orchestration library, device-memory contention belongs to the serving/scheduling layer, and a library that solves the first will silently do nothing for the second. Second, **a framework feature that assumes horizontal headroom (parallel subagents, concurrent tool calls) inverts into pure cost on hardware with a serialization invariant** -- check whether your constraint makes the selling point unusable before pricing the migration. **Reusable concept -- worth a spaced-repetition card (both).**

### [2026-09-21] Scoping agentic coding capability: edit format is the gating variable, not the agent loop
- Scoped what it would take to add Claude-Code-like coding capability to ALiRA2. Decomposed Claude Code into five layers (agent loop / context management / tool layer / permission-sandbox layer / harness UX) and found three already exist here: `_run_tool_loop`, the tool-result digest (a better-tuned version of output truncation), and the scoped-toolset discipline. Recommended adding a `"coding"` entry to `tooling/discovery.py`'s `TOOL_CATEGORIES` rather than building or adopting a separate agent, in the order: read-only tools (`read_file`/`glob`/`grep`) -> allowlisted `run_command` -> `edit_file`/`write_file` with a read-before-edit invariant and file-state tracking. Gated the whole thing behind a capability test to be added as MODEL_BENCHMARK Tier B6.
- Why this approach: the progressive tool-revelation mechanism already solves the cost objection -- coding tools would otherwise add to the ~2,780-token schema bill on every turn including the ones that never touch code, whereas a discoverable category costs nothing until revealed. It also inherits a real security boundary for free: `REMINDER_TOOLS`/`GMAIL_HOOK_TOOLS` deliberately omit `discover_tools`, so the autonomous hooks structurally cannot reach file-writing tools. Rejected adopting Aider/OpenHands wholesale for this use (they are better at coding today, but the novel thing here is the *combination* -- one loop that reads the user's papers, remembers their conversations, and patches their code), while noting that if the goal were only "an agent that edits my code", installing one of those is the correct answer and building is not. Also flagged Telegram as the wrong review surface for diffs, which argues for sequencing the planned Django frontend before the coding tools rather than after.
- What to remember: **for agentic code editing, the edit format is a model-capability dial, not a style choice, and it determines the token and latency budget of everything above it** -- whole-file rewrite works on weak models but burns enormous tokens (ruinous behind a `concurrency=1` queue), while search/replace diffs are cheap but require the model to reproduce existing text character-perfectly, which is exactly where small local models fail. Aider supports several formats precisely because of this, and benchmarks edit success per model. Hence: **measure the single hardest primitive before building the layers that depend on it** -- 10 exact search/replace blocks against a real file is half a day and gates a multi-week project. Second, transferable beyond coding: **the mechanisms that make an editing agent safe are correctness guards, not bureaucracy** -- read-before-edit stops the model inventing file contents, file-state tracking stops it clobbering concurrent changes, and exact-match-or-fail stops silent partial application; each exists because the failure it prevents is invisible otherwise. **Reusable concept -- worth a spaced-repetition card (first and third).**
- **Addendum:** checked the assumption that deepagents already ships most of this project's tools -- it does not, and the overlap is *zero*. deepagents provides ~8 built-ins (`write_todos`, the filesystem set `ls`/`read_file`/`write_file`/`edit_file` plus `glob`/`grep`, and `task` for subagents); this project has 27 registered tools across gmail/literature/documents/reminders/calendar/database/memory, and the sets are disjoint. The apparent overlap (`read_file` vs `read_document`) is not one: the latter reads marker-extracted markdown through an ownership-scoped, Postgres-tracked path. Design output: make `registry.py`'s `tool` decorator emit three views of the same function -- `TOOLS` (OpenAI schemas), `TOOL_FUNCTIONS` (plain callables, required by `live_viewer.py:70`), and `LC_TOOLS` (LangChain `StructuredTool`s for deepagents) -- while still `return fn`, so both loops can run side by side and the A/B costs nothing.
- **Concrete cost discovered, decision-relevant:** deepagents passes every registered tool on every call, so `discover_tools` -- which has no equivalent interception point in it and would have to be rebuilt as `wrap_model_call` middleware -- is not optional. Extrapolating this project's own measurements (~2,780 tokens at 12 tools, ~3,205 at 14, so ~212 tokens/tool): CORE_TOOLS' 9 tools cost ~2,100 tokens, all 27 cost ~6,000, and 27 plus a coding category ~7,300. Naive adoption therefore adds **~4,000 tokens to every model call**, on local models where context is already being bought with IQ3 quantization. **Transferable: when evaluating a framework, price its *defaults* against the optimisation you already built, because the default is usually "send everything" and your optimisation is usually invisible to it.**

### [2026-09-21] Reframe to a local coding agent: quantization is a verbatim-reproduction risk, and the serialization lock belongs in the adapter
- Goal changed from "research assistant with coding bolted on" to "Claude Code clone on local models", with a full rewrite acceptable and sequential subagents explicitly fine. Reversed the earlier recommendation and now advise building on deepagents: sequential subagents plus a coding goal is exactly its shape (filesystem backend, subagent isolation, todos, summarization), leaving bash, the permission layer, and the local-model adapter as the custom work. Rewrite deletes the research-assistant surface (Telegram, Gmail, calendar, reminders, hooks, marker-pdf, pgvector document RAG) and keeps `LLM_ROUTING`, `unload_all_models()`, and `turn_actions`/live viewer. Celery likely drops out entirely -- it existed to arbitrate cross-process GPU contention, and a single-user agent with sequential subagents needs a serialization primitive, not a distributed queue.
- Why this approach: two decisions carry the design. First, **the GPU serialization lock goes inside the custom `BaseChatModel._generate`, not in graph/middleware configuration** -- LangGraph's parallelism is governed by config, middleware and version, so an invariant enforced there is one upgrade away from silently breaking, whereas an adapter-level lock cannot be bypassed by any framework change (~5 lines, one choke point). This is the direct application of this project's own earlier lesson about documented-but-unenforced invariants. Second, rejected vector search over code in favour of glob + ripgrep, reserving embeddings for conversation summaries only: code has exact identifiers, so exact-match search beats semantic similarity for finding a definition, and code RAG tends to return plausible neighbours instead of the actual symbol.
- What to remember: **low-bit quantization degrades verbatim reproduction disproportionately, and agentic code editing is a verbatim task** -- search/replace edit blocks require reproducing existing file text character-perfectly, which is not what quantization benchmarks measure (they measure semantic/conversational quality). A model that reads fine at IQ3_XXS can be unusable for exact-match edits, so the right experiment is the *same* model at IQ3 vs Q4/Q5 scored on edit application, and the likely outcome is an explicit trade of context length against edit fidelity. Second, **enforce a resource invariant at the narrowest layer that every path must pass through, not at the layer where the policy is conceptually expressed** -- config expresses intent, a choke point guarantees it. Third: **a small context window makes subagents more valuable, not less** -- a fresh window that does one scoped job and returns only a digest is the main tool for fitting a large task into a small budget, which is the existing tool-result digest generalised to a bigger unit (including its known failure mode: the model distrusting system-inserted content as prompt injection, so subagent digests need explicit provenance too). **Reusable concept -- worth a spaced-repetition card (all three).**
- **Correction to the entry above:** the premise was wrong -- the research-assistant surface (Telegram, Gmail, calendar, reminders, documents/pgvector, marker-pdf) is the *specific* value of this project and stays. Coding capability is additive, via a new `"coding"` entry in `TOOL_CATEGORIES`. Consequently **Celery stays too**: marker-pdf/embeddings/local-chat VRAM contention is unchanged, so the "drop Celery for a simple lock" advice above applies only to a hypothetical coding-only rewrite that is not happening.

### [2026-09-21] Route-scoped concurrency: a queue that protects a resource must be skipped by calls that don't use it
- Designed how to vary concurrency between a local GPU backend (serialized) and a hosted API like Kimi K3 (parallel subagents wanted). Chose to extend `LLM_ROUTING` from `model -> endpoint string` to `model -> {endpoint, local, max_concurrency, retry, token_budget}`, accepting a bare string as the old shape for backwards compatibility, and to dispatch on `route.local`: local models go through the existing `concurrency=1` Celery "chat" queue, hosted models call directly bounded by a per-route semaphore. Parallel-subagent behaviour is derived (`max_concurrency > 1`), not a separate switch.
- Why this approach: the Celery chat queue exists solely to arbitrate 16.3GB of VRAM. A hosted API call consumes zero VRAM, so routing it through that queue would park it behind a marker-pdf ingestion for no reason -- structurally the same defect as the 352s stall of 2026-09-19, but harder to detect, since the model call itself would look fast in isolation and only the end-to-end latency would suffer. Also settled two details: the semaphore must be acquired per *model call*, not per subagent run (holding it across a multi-step subagent serializes at the wrong granularity and kills interleaving), and parallel subagents against a `max_concurrency=1` route degrade to sequential rather than deadlocking, because each branch acquires and releases independently -- one code path for both deployments, difference confined to config, but worth an explicit test since graceful degradation is exactly the property a framework upgrade can silently revoke.
- What to remember: **a queue that exists to protect a specific resource must be bypassed by work that doesn't consume that resource** -- otherwise the protection becomes unrelated head-of-line blocking, and it is hard to diagnose because each individual operation still looks fast. Generalises past GPUs to any shared-resource semaphore (DB connection pools, rate-limited APIs, disk I/O). Second, **when one deployment axis (local vs hosted) changes several settings at once -- concurrency, retry policy, cost budget, failure modes -- make it one object rather than several parallel flags**, so the settings cannot drift into an incoherent combination, and derive dependent behaviour (parallel subagents) from it instead of exposing a second switch that can contradict the first. **Reusable concept -- worth a spaced-repetition card (both).**

### [2026-09-21] Dropping Celery: a manual trigger replaces scheduling policy, not the enforcement mechanism
- Evaluated removing Celery/Redis in favour of a user-clicked "digest docs" button that pauses everything during ingestion. Conclusion: viable, but the button alone is insufficient. Replacement is an `asyncio.Semaphore(route.max_concurrency)` in the model adapter plus an on-demand `multiprocessing.Process` for ingestion (parent holds the semaphore for its duration, progress relayed as JSON lines over a pipe). Deciding question left with the user: whether the multi-machine scaling that ARCHITECTURE.md explicitly designs for (base64 PDF bytes in task args so ingestion can run on another host) is a real goal or aspirational -- it is the only capability with no cheap substitute. Live finding along the way: the chat/literature priority switch is dead code -- `ingestion_tasks.dispatch_ingestion` accepts a `queue` argument but its only caller passes `"chat"`, and `run_gpu_task` hardcodes `"chat"`, so nothing ever dispatches to `literature` despite the switch having been built and verified.
- Why this approach: Celery currently provides six things, of which only two survive scrutiny -- a cross-process GPU mutex and out-of-process execution for marker-pdf (so surya/torch models don't stay resident in a long-lived bot process). A per-document subprocess covers the second for free, since process exit reclaims VRAM and torch state, and an in-process semaphore covers the first once ingestion is coordinated through it. The deletion also removes two workarounds that exist *only because of* Celery: the `in_celery_worker()` deadlock guard, and `pdftext_workers=1` -- that AssertionError came from Celery's prefork pool marking children daemonic, and a plain subprocess is not daemonic, so pdftext's own parallelism becomes usable again.
- What to remember: **a manual trigger changes scheduling policy but cannot enforce an invariant** -- the button gates the *user's* path while the autonomous hook ticker (`asyncio.create_task`, fires reminders/Gmail polls with no user present) walks straight through any check living in the button handler or an `is_ingesting` flag. Enforcement must sit in the one choke point every path traverses, which here is the semaphore every model call already acquires. This is the same shape as the adapter-lock and route-concurrency decisions from earlier today, so it is a standing principle for the rewrite, not three separate findings: **resource invariants belong at the narrowest common choke point, because that is the only place future code cannot forget them.** Second, and generally useful when deciding whether to remove infrastructure: **enumerate what it actually provides today versus what it was designed to provide** -- here two of six capabilities were load-bearing, two were unused (multi-machine, priority switching), and two had cheaper substitutes; the audit also surfaced that removing the infrastructure removes its workarounds too, which is a benefit that never shows up if you only price the migration. **Reusable concept -- worth a spaced-repetition card (both).**
